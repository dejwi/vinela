# Architecture

> Deep dive into the lua-generator's 9-phase pipeline, data flow, key abstractions, and error handling.

## The 9-Phase Generation Pipeline

The orchestrator (`orchestrator/phase-coordinator.ts`, 661 lines) coordinates the entire generation process through 9 sequential phases. Each phase reports progress via the `onProgress` callback and checks for cancellation via `AbortSignal`.

```
Phase 1: Prepare Context          Validate project path, check cancellation
Phase 2: Data Loading             Load all project data in parallel
Phase 3: Pre-Generation Checks    Run 11 diagnostic checks
Phase 4: Compute Disable States   Filter enabled graphs, partition by state
Phase 5: Section Generation       Generate 7 config sections
Phase 6: Graph Generation         Traverse + generate code for all graphs
Phase 7: Assembly                 Assemble final init.lua in canonical order
Phase 8: Post-Generation Valid.   (Reserved for future syntax validation)
Phase 9: Finalize Result          Build metadata, return GenerationResult
```

### Phase Details

#### Phase 1: Prepare Context
- Validates `projectPath` is non-empty
- Checks `AbortSignal` for early cancellation
- Minimal work -- just guards

#### Phase 2: Data Loading
**File:** `orchestrator/data-loader.ts` (381 lines)

Loads all project data in parallel using `Promise.all` with per-source safe wrappers. Each data source returns a `LoadOutcome<T>` discriminated union:

```typescript
type LoadOutcome<T> =
  | { status: 'success'; data: T }
  | { status: 'missing'; data: T }   // File not found, use default
  | { status: 'error'; error: string; data: T }  // Load failed, use default
```

**Data sources loaded:**
| Source | Type | Fatal if missing? |
|--------|------|-------------------|
| Graphs | `Graph[]` | Yes (empty array = no-op, error = fatal) |
| Plugins | `InstalledPlugin[]` | No |
| Schemas | `PluginSchema[]` | No |
| Neovim Options | `ProjectNeovimOptionsFile \| null` | No |
| Keymaps | `ProjectKeymap[]` | No |
| Profiles | definitions plus local overrides | No |
| LSP Config | `ProjectLspConfig` | No |
| Colorscheme Prefs | `{ activeScheme, variantPreferences }` | No |

Only graph loading failure is fatal. All other sources gracefully degrade to defaults. A local profile-state read failure retains tracked definitions and applies their defaults.

#### Phase 3: Pre-Generation Checks
**File:** `orchestrator/pre-generation-checks.ts` (48 lines)

Runs all 11 diagnostic checks (see [Diagnostics](./diagnostics.md)). If any **errors** are found, generation aborts immediately. Warnings are collected but don't block generation.

Note: `assertSchemaShape` enforces effective-key syntax/uniqueness only. Raw-vs-typed subtree overlap is enforced at config time by `assertNoRawTypedSubtreeOverlap` in `plugin-section.ts`.

Plugin setup generation is schema-driven: phase 5 interprets generic option metadata, generation rules, and plugin capabilities declared in schema JSON. Do not add named-plugin generator branches when a schema needs new behavior.

#### Phase 4: Compute Disable States
Uses `computeDisableStates()` from the graph-editor feature to partition graphs:
- **Enabled graphs** -- sorted by canonical order (`order` field, then `updatedAt`, then `id`)
- **Excluded graphs** -- user-disabled or dependency-disabled, emitted as warnings

#### Phase 5: Section Generation
Generates 7 independent config sections sequentially (see [Sections](./sections.md)):

1. Leader Key (`vim.g.mapleader`)
2. Neovim Options (`vim.opt.*`)
3. Plugins (`vim.pack.add()` + `require().setup()`)
4. LSP (`vim.lsp.enable()` + Mason)
5. Colorscheme (`vim.cmd.colorscheme()`)
6. Highlights (`nvim_set_hl()`)
7. Project Keymaps (`vim.keymap.set()`)

Each section returns a `SectionResult` with code lines and diagnostics.
Unprofiled or unknown-only manual keymaps use `enabled`; keymaps with defined profile assignments use `enabledOverride` when present, otherwise active-profile OR state. Graph and schema keymaps are unaffected.

#### Phase 6: Graph Generation
**File:** `orchestrator/graph-generation.ts` (58 lines)

This is where the graph visual editor's nodes become Lua code. The process:

1. Build traversal indexes for all enabled graphs (`buildGraphIndexes`)
2. Extract callable contracts from graphs with Callable Entry nodes
3. Traverse **callable graphs first** (they define functions other graphs may call)
4. Traverse **startup/trigger graphs second** (they call those functions)

Returns `{ callableUnits, startupUnits }` -- arrays of `CompilationUnit[]`.

#### Phase 7: Assembly
**File:** `orchestrator/assemble.ts` (140 lines)

Assembles the final `init.lua` string in canonical order:

```lua
-- ============================================
-- Generated by vinela
-- Project: MyProject
-- Generated: 2026-03-04T12:00:00.000Z
-- ============================================

_G._vinela_callables = _G._vinela_callables or {}

-- Section: leader-key
vim.g.mapleader = " "

-- Section: neovim-options
vim.opt.number = true
...

-- Section: callable-functions
_G._vinela_callables["graph-id"] = function(params)
  ...
end

-- Section: plugins
vim.pack.add("nvim-treesitter/nvim-treesitter")
...

-- Section: lsp
...

-- Section: colorscheme
pcall(vim.cmd.colorscheme, "catppuccin")

-- Section: highlights
...

-- Section: project-keymaps
vim.keymap.set("n", "<leader>f", ...)

-- Startup Execution
do
  vim.opt.number = true
  ...
end
```

#### Phase 8: Post-Generation Validation
Currently a placeholder. Reserved for future Lua syntax validation (luacheck, `nvim --headless`).

#### Phase 9: Finalize Result
Builds `GenerationMetadata` with stats:
- `graphsGenerated`, `nodesGenerated`, `pluginsConfigured`
- `linesOfCode`
- `generationTimeMs`
- `phaseTimingsMs` (per-phase breakdown)

## Key Abstractions

### CompilationUnit

The intermediate representation between traversal and assembly. **Entry-point nodes** (triggers, callable-entry) and linear action nodes each produce one `CompilationUnit`. However, **branch and body nodes** (e.g. nodes inside `if`/`then`, loop bodies) are generated **inline** inside the parent node's code via `renderExecFromPort` and are **not** pushed as separate units to the output array. This prevents double-emission and keeps indent structure correct:

```typescript
interface CompilationUnit {
  nodeId: string                          // Source node ID
  nodeType: string                        // e.g., 'trigger', 'action'
  code: string[]                          // Generated Lua lines
  localVars: string[]                     // Local variables declared
  inputBindings: Record<string, string>   // portId -> variable expression
  outputBindings: Record<string, string>  // portId -> variable name
  indentLevel: number                     // Nesting depth
}
```

### GenerationContext (Node Generator Context)

Passed to every node generator. Provides everything a generator needs:

```typescript
interface GenerationContext {
  // Graph info
  readonly graphId: string
  readonly graphName: string
  readonly nodeById: ReadonlyMap<string, GraphNode>
  readonly edges: readonly GraphEdge[]
  readonly indexes: GraphIndexes

  // Input resolution
  readonly inputBindings: Readonly<Record<string, string>>
  readonly getInputValue?: (portId: string) => string

  // Output hints
  readonly outputBindingHints: Readonly<Record<string, string>>

  // Code generation helpers
  readonly indentLevel: number
  readonly renderExecFromPort: (nodeId: string, sourcePortId: string) => string[]
  readonly sanitizeIdentifier: (raw: string) => string
  readonly toLuaLiteral: (value: unknown) => string
  readonly getVariableName: (hint?: string) => string

  // Diagnostics
  readonly emitDiagnostic: (diagnostic: GenerationDiagnostic) => void

  // Cross-graph references
  readonly callableSymbolByGraphId: ReadonlyMap<string, string>
  readonly callableContracts?: ReadonlyMap<string, CallableContract>
}
```

### GenerationResult (Discriminated Union)

The top-level result type:

```typescript
type GenerationResult =
  | { success: true; initLua: string; diagnostics: GenerationDiagnostic[]; metadata: GenerationMetadata }
  | { success: false; diagnostics: GenerationDiagnostic[]; metadata: GenerationMetadata; initLua?: string }
```

### DiagnosticsCollector

Non-failing accumulator with automatic deduplication. See [Diagnostics](./diagnostics.md).

### LuaBuilder

Fluent API for generating Lua code with automatic indentation. See [Node Generators](./node-generators.md#luabuilder-api).

## Data Flow: Graphs to Lua

Here's the complete data flow for a single graph:

```
Graph (nodes + edges)
    |
    v
buildGraphIndexes()          -- O(V+E) indexing
    |                           Classifies edges as exec vs data
    |                           Finds entry nodes (triggers, callable-entry)
    v
IndexedGraph
    |-- nodesById: Map<string, GraphNode>
    |-- outgoingExecByNode: Map<string, ExecEdge[]>
    |-- incomingDataByNode: Map<string, DataEdge[]>
    |-- incomingDataByTargetPort: Map<string, Map<string, DataEdge[]>>
    |-- entries: string[]
    |
    v
traverseExecFlow()           -- DFS from each entry node
    |                           For each node:
    |                             1. resolveDataDependencies() -- Kahn's algorithm
    |                             2. resolveGeneratorType()    -- determine generator key
    |                             3. getGenerator()            -- lookup in registry
    |                             4. generator.generate()      -- produce CompilationUnit
    |                             5. Register output bindings
    |                             6. Follow exec edges to next node
    v
CompilationUnit[]
    |
    v
assembleFinalInitLua()       -- Combine sections + graph units
    |                           Apply canonical ordering
    |                           Add header, registry init
    v
init.lua (string)
```

## Error Handling Strategy

### Non-Failing Accumulation

The generator uses a **non-failing accumulation** pattern. Instead of throwing on the first error, it collects all diagnostics and continues as far as possible:

```typescript
const collector = new DiagnosticsCollector()

// Phase 3: Collect all pre-generation issues
runPreGenerationChecks(ctx, collector)

// Only abort if there are errors (not warnings)
if (collector.hasErrors()) {
  return buildErrorResult(collector, startTime)
}

// Phase 6: Node generators emit diagnostics but don't throw
generator.generate(node, {
  emitDiagnostic: (d) => collector.addWarning(d),
  ...
})
```

### Abort Points

The pipeline checks `AbortSignal` at these points:
- After Phase 1 (prepare)
- After Phase 2 (data loading)
- After Phase 5 (sections)
- During Phase 6 (per-graph)

### Timeout Protection

The store wraps generation with timeouts:
- **Import timeout:** 10 seconds for dynamic imports
- **Generation timeout:** 60 seconds for the entire pipeline

### Error Categories

```typescript
type DiagnosticCategory =
  | 'structure'      // Graph structure issues (empty, duplicates)
  | 'connectivity'   // Unreachable nodes, missing connections
  | 'config'         // Invalid configuration values
  | 'syntax'         // Lua syntax issues
  | 'reference'      // Invalid graph/node references
  | 'cycle'          // Circular dependencies
  | 'runtime'        // Unexpected runtime errors
```

## Domain Boundaries

The lua-generator is organized into domains with clear boundaries:

| Domain | Module | Responsibility |
|--------|--------|---------------|
| D1 | `utils/` | Lua code building primitives |
| D2 | `traversal/` | Graph indexing and traversal |
| D3 | `generators/nodes/` | Per-node-type code generation |
| D4 | `sections/` | Top-level config sections |
| D5 | `orchestrator/` | Pipeline coordination |
| D6 | `diagnostics/` | Pre-generation validation |
| D7 | `deploy/` | File system operations |
| D8 | `components/`, `hooks/`, `store.ts` | UI and state management |

**Key rule:** Lower domains never import from higher domains. D2 (traversal) never imports from D5 (orchestrator). D3 (generators) never imports from D5. The orchestrator wires everything together.
